# 生产环境与实验环境的差异

## 1. 为什么必须先理解差异

在笔记本上搭出来的集群，和生产集群的差距不只是「节点少」。如果不知道哪些差异是本质的，很容易把实验结论直接套到生产，或者在面试里说不出所以然。

## 2. 一张对比表

| 维度 | 生产环境 | 笔记本实验 | 差距是否影响原理 |
|---|---|---|---|
| 规模 | 数百节点、多集群 | 1～3 个虚拟机 | 影响容量和性能，不影响链路 |
| 高可用 | 多副本、跨可用区、故障转移 | 单点 | 影响可靠性设计 |
| 存储 | 对象存储、分布式块存储、长期保留 | local-path、短期保留 | 影响成本和查询范围 |
| 采集 | DaemonSet + Gateway + 缓冲 | 单层 Agent | 影响背压和扩展性 |
| 权限 | RBAC、审计、审批、最小权限 | 通常是 admin | **影响 AI 运维能否落地** |
| 变更 | 灰度、回滚、变更窗口 | 随时改 | 影响故障归因 |
| 告警 | 分级、抑制、值班、升级 | 一个 webhook | 影响告警质量 |
| 故障 | 真实流量、真实故障 | 人工注入 | 影响演练真实性 |
| 成本 | 按 GB/序列计费，需要优化 | 基本不关心 | 影响架构选型 |
| 合规 | 数据脱敏、审计、留存 | 通常忽略 | 影响 AI 接入方式 |

## 3. 哪些能迁移，哪些不能

### 能迁移的（实验里要重点练）

- **数据模型**：指标、日志、链路的字段和标签设计。
- **链路顺序**：采集 → 缓冲 → 存储 → 查询 → 告警 → 消费。
- **查询语言**：PromQL、LogQL、TraceQL。
- **告警语义**：pending / firing / resolved，分组、抑制、静默。
- **AI 接入点**：上下文怎么组装、证据怎么引用、工具怎么定义。
- **权限模型**：ServiceAccount、Role、RoleBinding 的实际写法。

### 不能直接迁移的（知道即可，别硬套）

- 具体容量数字和性能调优参数。
- 高可用拓扑和跨区容灾。
- 真实流量的长尾分布。
- 组织级的 on-call 流程和变更审批。
- 商业存储/监控平台的成本模型。

## 4. 在笔记本上「模拟」生产

### 4.1 用资源限制制造真实约束

给 demo 服务和监控组件设置 `requests` / `limits`，故意让节点资源紧张。观察：

- Pod 被 OOMKilled 时，指标和事件长什么样。
- 节点压力驱逐（eviction）如何发生。
- Prometheus 内存不够时，抓取会怎么失败。

### 4.2 用故障注入代替真实故障

按难度递增：

1. 删除 Pod，观察 Deployment 重建、告警触发。
2. 用 `stress-ng` 打满 CPU/内存。
3. 制造 DNS 解析失败、依赖超时。
4. 填满磁盘，观察 kubelet 驱逐和日志采集中断。
5. 用 Chaos Mesh 做网络延迟、分区、Pod Kill。

每次注入都要记录：**预期现象、实际现象、告警是否触发、AI 摘要是否准确**。

### 4.3 用 SLO 代替「感觉还行」

给 demo 服务定义：

- SLI：可用性 = 成功请求 / 总请求；延迟 = P95 < 300ms。
- SLO：30 天可用性 99.5%。
- 错误预算：剩余多少、燃烧率多快。

这样才能练习「告警该不该响」这个真实问题。

### 4.4 用流程模拟变更管理

- 所有改动走 Git，不直接 `kubectl edit`。
- 用 ArgoCD 或简单的 CI 做发布。
- 每次变更记录时间、内容、影响范围。
- 出故障后写 postmortem：时间线、根因、改进项。

这些流程在笔记本上完全可以跑，而且比多装几个组件更能体现 SRE 思维。

## 5. 硬件分级

VMware 上能跑什么，取决于宿主机内存。建议先确认自己的配置，再选方案。

| 方案 | 宿主机内存 | 虚拟机 | 集群 | 能做的实验 |
|---|---|---|---|---|
| A 轻量（本机） | 16 GB | 3 台：6G + 2G + 2G | k3s 三节点 | 指标、日志、告警、AI 摘要、节点故障 |
| B 标准 | 32 GB | 3 台：8G + 6G + 6G | kubeadm 或 k3s | 加上链路追踪、更多副本、Chaos Mesh |
| C 完整 | 64 GB | 3～4 台 | kubeadm 三节点 + 独立监控 VM | 加上存储、HA、多租户 |

> 16 GB 的关键取舍：用 k3s 换控制面内存，把监控栈集中在 server 节点，worker 只跑业务和采集 Agent。详见 [实验设计](../02-lab/00-lab-design.md)。

> 内存不足时，优先砍掉「高可用」和「长期存储」，不要砍掉「日志链路」和「AI 接入」——后者才是求职时最能讲的部分。

## 6. 简历和面试怎么用

### 简历 bullet 示例

- 在 3 节点 Kubernetes 集群部署 Prometheus、Grafana、Loki、Fluent Bit、OpenTelemetry Collector，打通指标、日志、链路三条数据流，统一 namespace/pod/service 标签。
- 实现告警上下文聚合服务：接收 Alertmanager webhook，按时间窗口聚合指标、日志、K8s Event 和发布记录，调用 LLM 输出带证据的故障摘要。
- 设计受控运维 Agent：基于最小权限 ServiceAccount，动作白名单 + dry-run + 人工审批 + 审计日志，仅开放 restart/scale 等低风险操作。
- 使用 Chaos Mesh 注入 Pod 故障、CPU 压力、网络延迟，验证告警与 runbook，输出 postmortem。

### 面试高频追问

- 一条日志从产生到被查询，经过哪些组件？
- 为什么 Prometheus 用拉模型？标签基数怎么控制？
- Loki 和 ES 怎么选？
- 告警为什么会抖？怎么抑制？
- AI 怎么拿到上下文？token 超了怎么办？
- 怎么防止模型误删资源？
- 你怎么证明这个 AI 功能有效？

## 7. 一句话总结

实验环境可以缩小规模，但不能省略「链路」和「约束」。把权限、审计、成本、故障注入这些生产约束加进去，笔记本上的项目才有说服力。
