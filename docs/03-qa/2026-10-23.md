### 2. 为什么 Tempo 第一次安装失败在下载 chart？

#### 问题

`helm upgrade --install tempo ...` 报错：

```text
Get "https://github.com/grafana-community/helm-charts/releases/download/tempo-3.2.1/tempo-3.2.1.tgz":
read tcp 172.25.254.10:53038->20.205.243.166:443: read: connection reset by peer
```

#### 结论

失败发生在 Helm 下载 chart 压缩包阶段，不是 Kubernetes 资源、values 或镜像问题。`k8s-server` 访问 GitHub Releases 的下载连接被重置。

处理方式：

1. 在 Windows 下载同一官方 chart：`tempo-3.2.1.tgz`。
2. 校验 `SHA256` 和 `Chart.yaml` 里的 `version: 3.2.1`、`appVersion: 3.1.1`。
3. `scp` 到 server 的 `/root/tracing/`。
4. 用本地 chart 安装：

```bash
helm upgrade --install tempo ./tempo-3.2.1.tgz \
  -n tracing \
  --create-namespace \
  -f values-tempo.yaml \
  --wait \
  --timeout 10m
```

#### 验证

```bash
sha256sum tempo-3.2.1.tgz
tar -xOf tempo-3.2.1.tgz tempo/Chart.yaml | grep -E 'version:|appVersion:'
helm list -n tracing
```

预期 chart 版本 `3.2.1`、appVersion `3.1.1`，release `tempo` 为 `deployed`。

### 3. Tempo 日志里的 `no jobs found` 是故障吗？

#### 问题

`kubectl logs -n tracing tempo-0` 反复出现：

```text
level=error ... msg="error calling scheduler" err="rpc error: code = NotFound desc = no jobs found"
```

#### 结论

这是 Tempo 3 在空闲、没有 compaction/backend 任务时的已知日志噪声。当前：

- `tempo-0` 是 `1/1 Running`。
- `/ready` 返回 `ready`。
- OTLP 端口 `4317/4318` 正在监听。
- PVC 已 `Bound`。

所以不要为了让日志“看起来干净”去改 backend scheduler/worker；等有 trace 数据后再观察是否仍然持续报错。如果之后出现查询失败或 `/ready` 不健康，再单独排查。

### 4. 为什么 Collector 日志提示 `otlp` 别名弃用？

#### 问题

Collector 启动日志出现：

```text
"otlp" alias is deprecated; use "otlp_grpc" instead
```

#### 结论

Collector `0.163.2` 中 OTLP/gRPC exporter 的当前名字是 `otlp_grpc`，`otlp` 是兼容别名。receiver 仍然叫 `otlp`，不要一起改。

配置应从：

```yaml
exporters:
  otlp:
    endpoint: tempo.tracing.svc.cluster.local:4317
```

改为：

```yaml
exporters:
  otlp_grpc:
    endpoint: tempo.tracing.svc.cluster.local:4317
```

并同步修改 pipeline 的 exporter 名称。改完后重新应用 Collector 清单，确认日志不再出现该 warning。

#### 实际结果

```bash
kubectl apply -f otel-collector.yaml
kubectl rollout restart deployment/otel-collector -n tracing
kubectl rollout status deployment/otel-collector -n tracing --timeout=120s
kubectl logs -n tracing deploy/otel-collector --tail=80 | grep -F 'deprecated' || echo 'no deprecation warning'
```

结果：

- `otel-collector` 新 Pod 为 `1/1 Running`，Deployment `AVAILABLE 1`。
- 日志重新出现 `Everything is ready. Begin running and processing data.`
- 最后输出 `no deprecation warning`。
- Task 2 已提交：`1a57f47 feat: add otel collector`。

### 5. 为什么 Tempo 放 `k8s-server`，Collector 放 `k8s-worker-1`？

#### 结论

- `k8s-server` 内存 6 GB，当前使用 52%，磁盘 60 GB，适合放带 PVC 的 Tempo。
- `k8s-worker-1` 当前内存 45%，Collector 只有 `64Mi` 请求、`128Mi` 上限，放这里不会和 Tempo 抢内存。
- `k8s-worker-2` 已经有 Loki，继续保留，避免日志和追踪后端挤在同一节点。
- 应用通过 ClusterIP Service 访问 Collector，不需要关心 Pod 在哪个节点。
