### 6. 为什么日志每 5 秒多一条 `hello from log-demo`？

#### 问题

只手动请求了一次 `/`，但 `kubectl logs` 里连续出现多条：

```text
{"level": "info", "trace_id": "...", "message": "hello from log-demo"}
```

时间间隔正好约 5 秒。

#### 结论

这是 Kubernetes readiness probe 请求 `/` 造成的。Deployment 里配置了：

```yaml
readinessProbe:
  httpGet:
    path: /
  periodSeconds: 5
```

每次探针请求都会进入 `do_GET()`，在 `/` 分支里创建 span 并写 info 日志，所以 Tempo 和 Loki 会被探针数据污染；验收时也无法区分“手动请求”和“探针请求”。

修正方式：

- 新增 `/healthz`，在创建 span 之前直接返回 200，不写日志、不生成 trace。
- readiness probe 改为请求 `/healthz`。
- startup probe 仍然是 TCP 检查，不受影响。

```python
def do_GET(self):
    path = urlparse(self.path).path

    # 探针不生成 trace/log，避免每 5 秒污染 Tempo 和 Loki
    if path == "/healthz":
        self._send(200, "ok\n")
        return
```

```yaml
readinessProbe:
  httpGet:
    path: /healthz
```

#### 验证

```bash
# 应用后等待 15 秒，不手动请求
kubectl logs -n demo deploy/log-demo --since=15s
```

预期没有新的 `hello from log-demo` 日志。再手动请求 `/`：

```bash
kubectl exec -n demo deploy/log-demo -- \
  python -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:8080/").read().decode().strip())'

kubectl logs -n demo deploy/log-demo --tail=10
```

预期只多一条 `hello from log-demo`，并且 `trace_id`/`span_id` 都是有效十六进制。

#### 实际结果

- 滚动更新完成后只剩新 Pod `log-demo-998849ff9-qxksv`。
- 新 Pod readiness 路径为 `/healthz`。
- 旧 Pod 退出后，新 Pod 日志只有一条手动 `/` 请求，没有每 5 秒的探针日志。
- 手动 `/healthz` 和 `/` 都返回 `ok`；`/healthz` 没有写日志。
- 说明：滚动更新期间 `kubectl logs deploy/log-demo` 会提示找到 2 个 Pod，并可能选到旧 Pod；排查时要按 Pod 名分别看日志。

### 7. 为什么 Tempo 搜索返回的 traceID 和日志里的不一样？

#### 问题

日志里的 `trace_id` 是：

```text
651bd0d1467a24fcc112b750f88f0027
```

但 Tempo 搜索接口返回的 5 条 trace 是：

```text
3da9c58843393756228588b07b843c16
591ca7b69a8a98c1e7cb749df46a7d65
...
```

看起来完全对不上。

#### 结论

有三个原因：

1. `limit=5` 只是返回一个子集，不能用来判断某条 trace 是否存在。那次返回的 5 条是修复探针之前旧 Pod 留下的 `GET /` 探针 trace。
2. 旧 Pod 已经退出，但它已经发到 Tempo 的 trace 不会自动消失；在实验环境里可以忽略，或者等 Tempo 保留期到期。
3. Tempo 的 OTLP JSON 接口里，`traceId`/`spanId` 是 base64 编码；应用日志里是十六进制。两者是同一个值，只是编码不同。

例如：

```text
base64: ZRvQ0UZ6JPzBErdQ+I8AJw==
hex:    651bd0d1467a24fcc112b750f88f0027
```

#### 验证

按 trace ID 精确查询：

```bash
kubectl exec -n demo deploy/log-demo -- \
  python -c 'import urllib.request; print(urllib.request.urlopen("http://tempo.tracing.svc.cluster.local:3200/api/traces/651bd0d1467a24fcc112b750f88f0027").read().decode())'
```

实际返回包含：

- `demo.hello` 子 span
- `GET /` 根 span
- `service.name=log-demo`
- `http.response.status_code=200`

#### 实际结果

Tempo 返回了完整 span 树，说明应用日志里的 `trace_id`、Collector、Tempo 三者已经正确关联。Task 3 已提交：`c3e2c04`。

#### 结论

这是 Grafana 版本的按钮名称差异。当前版本显示 **Related logs**，它使用的仍然是 Tempo 数据源的 `tracesToLogsV2` 配置，不是另一个功能。

点击后 Grafana 自动生成：

```logql
{namespace="demo", pod=~"log-demo-.*"} | json | line_format "{{.log}}" | json | trace_id="fada9c248ccea6ea3f7525787bd888af"
```

#### 实际结果

Loki 返回 1 条 error 日志，trace ID 与 Tempo 页面一致，说明 Tempo → 日志方向也打通。

### 9. 为什么 `/metrics` 测试不能只看 HTTP 200？

#### 问题

第一次测 `/metrics` 时，`urlopen` 成功返回，误以为指标端点已经存在。实际 demo 的 catch-all 对任何未知路径都返回 `200 ok`。

#### 结论

对指标端点不能只看状态码，要检查响应正文是否包含指标名，例如 `demo_http_requests_total`，或者检查 `Content-Type` 是否为 Prometheus 文本格式。

#### 实际结果

```text
status=200 body= ok\n
RED: /metrics is not Prometheus metrics yet
command terminated with exit code 1
```

说明“HTTP 200”只代表请求被处理了，不代表 Prometheus 指标已经实现。

### 10. 为什么 PrometheusRule 应用后第一次查询还是空？

#### 问题

`kubectl apply` 之后立刻查询 `demo:sli_availability:ratio_rate5m`，结果还是 `[]`。

#### 结论

`PrometheusRule` 不是立即生效的。链路是：

```text
kubectl apply
  -> Prometheus Operator 发现 PrometheusRule
  -> 生成 Prometheus 规则文件
  -> Prometheus reload
  -> 等待下一个 evaluation interval（30s）
  -> recording rule 才产生第一条样本
```

所以刚 apply 时查不到是正常的，等 1–2 个计算周期再查。

#### 实际结果

```text
第一次查询：
demo:sli_availability:ratio_rate5m => []
demo:error_budget_burn_rate5m => []

约 30 秒后：
demo:sli_availability:ratio_rate5m => 1
demo:error_budget_burn_rate5m => 0
```

如果 60 秒后仍然为空，才需要检查 `PrometheusRule` 是否被 `ruleSelector` 选中、Prometheus 是否 reload 成功，以及原始指标 `demo_http_requests_total` 是否存在。

### 11. 为什么 `DemoNoTraffic` 是 pending，而不是 firing？

#### 问题

停掉 loadgen 6 分钟后查询：

```promql
ALERTS{alertname="DemoNoTraffic"}
```

返回的 `alertstate` 是 `pending`，不是 `firing`。

#### 结论

`ALERTS` 指标同时包含 pending 和 firing 两种状态：

- `pending`：告警表达式已经为真，但还没有满足 `for` 指定的持续时间。
- `firing`：已经满足 `for`，正在告警。

`DemoNoTraffic` 配置了：

```yaml
for: 10m
```

所以停流量 6 分钟时它只能是 pending；到 10 分钟才会变成 firing。

验证 fast/slow burn 时应该查：

```promql
ALERTS{alertname=~"DemoAvailability(Fast|Slow)Burn"}
```

如果要只看真正 firing 的告警，必须加：

```promql
ALERTS{alertstate="firing"}
```

否则容易把 pending 误判成已经告警。

#### 实际结果

```text
停流量 6 分钟：
fast/slow burn => []
DemoNoTraffic => pending
sum(rate(demo_http_requests_total[5m])) => 0

恢复 loadgen 60 秒后：
sum(rate(demo_http_requests_total[5m])) => 0.495
Demo.* => []
```

### 12. 为什么 AlertmanagerConfig 生成后，合成告警一开始可能不匹配？

#### 问题

`AlertmanagerConfig` 已经创建，生成配置里也有 receiver，但告警可能不走自定义路由，或者抑制规则不生效。

#### 结论

Prometheus Operator 的 `AlertmanagerConfig` 默认使用：

```yaml
alertmanagerConfigMatcherStrategy:
  type: OnNamespace
```

含义是：

> 这个 AlertmanagerConfig 只处理带有 `namespace` 标签，且值等于该 AlertmanagerConfig 所在命名空间的告警。

本实验的 AlertmanagerConfig 在 `monitoring`，所以告警必须带：

```yaml
namespace: monitoring
```

Operator 会自动把它转换成生成配置里的：

```yaml
matchers:
  - namespace="monitoring"
```

如果告警没有这个标签，路由和抑制规则都不会匹配。

因此：

- `DemoAvailabilityFastBurn`、`DemoAvailabilitySlowBurn`、`DemoNoTraffic` 的告警标签都补了 `namespace: monitoring`。
- 通过 Alertmanager API 注入的合成告警也都带 `"namespace": "monitoring"`。

#### 实际结果

```text
alertmanagerConfigSelector => {}
alertmanagerConfigNamespaceSelector => {}
alertmanagerConfigMatcherStrategy => 空，默认 OnNamespace

生成配置中：
matchers:
- namespace="monitoring"

补标签后：
TestCritical -> /webhook/critical
TestGroup -> /webhook/warning
TestInhibitWarning -> suppressed
```

#### 常见错误

- 只给 `PrometheusRule` 加 `namespace: demo`，但 AlertmanagerConfig 在 `monitoring`，仍然不匹配。
- 合成告警忘了 `namespace`，路由测试看起来“配置正确但没通知”。
- 把 matcher strategy 改成 `None` 可以让所有告警匹配，但会扩大配置作用范围；本实验没有这么做。

### 13. FastBurn 恢复了，为什么 SlowBurn 反而 firing？这是实验失误吗？

#### 问题

loadgen 切回 `/` 后：

```text
DemoAvailabilityFastBurn => resolved
DemoAvailabilitySlowBurn => firing
```

看起来像“恢复了反而报警”，是不是配置错了？

#### 结论

不是操作失误，也不是告警规则错误。更准确的定性是：

```text
长窗口告警的预期延迟行为
+ 测试没有隔离 SlowBurn
+ 6h 窗口包含额外历史错误
```

SlowBurn 的条件是：

```promql
demo:error_budget_burn_rate30m > 6
and
demo:error_budget_burn_rate6h > 6
```

故障期间的 500 会留在 30m 和 6h 窗口里。恢复流量后：

- 5m 窗口很快变干净，所以 FastBurn 恢复。
- 30m/6h 窗口仍然包含错误，所以 SlowBurn 的条件仍然成立。
- `for: 15m` 满足后，SlowBurn 才进入 firing。

因此它比 FastBurn 更晚触发，也更晚恢复。

另外，12 分钟全错误按 6h 窗口计算，燃烧率大约只有：

```text
12 / 360 / 0.01 ≈ 3.3x
```

不应该超过 6。实际看到 `11.13x`，说明 6h 窗口里还有更早的 500，或者 `rate()` 在数据不足时有外推。这是实验基线没有完全隔离/存在历史数据的表现，但不是路由错误。

#### 实际结果

```text
13:06:39  FastBurn firing
13:20:09  SlowBurn firing
13:22:09  FastBurn resolved
13:22:19  webhook 收到 SlowBurn firing 和 FastBurn resolved
```

等待自然恢复需要接近 6 小时，因为错误要逐条老化出 6h 窗口。本实验没有等待，记录为已知偏差。

#### 处理原则

- 不通过改阈值让 SlowBurn 消失，否则会掩盖 SLO 设计。
- 不把 SlowBurn 说成 resolved；它仍然是 firing。
- 如果只是实验环境清理，可以创建带注释的临时静默，但文档必须说明“静默不等于恢复”。
- 验收时以 FastBurn 的完整链路为主要目标；SlowBurn 的长窗口行为单独记录为偏差。

### 14. 为什么 `/metrics` 不能走 trace 和业务日志逻辑？

#### 问题

demo 的 `/metrics` 和 `/healthz` 为什么要绕开普通请求的 span、日志和计数？

#### 结论

`/metrics` 会被 Prometheus 每 15 秒抓取一次。如果它也进入业务逻辑：

- 每次抓取都会创建 trace，污染 Tempo
- 每次抓取都会写日志，污染 Loki
- 每次抓取都会增加 `demo_http_requests_total`，指标自己污染自己

`/healthz` 被 readiness/liveness probe 周期性请求，问题更明显：每 5 秒一条日志、一个 trace。

因此这两个路径在创建 span 和写业务日志之前直接返回。

### 15. 为什么 99% SLO 的燃烧率分母是 0.01？

SLO 是 99%，允许的错误比例是：

```text
1 - 0.99 = 0.01
```

燃烧率表示“当前错误速度是允许速度的多少倍”：

```text
当前错误比例 / 0.01
```

如果当前错误比例是 0.02，燃烧率就是 2x；如果允许错误比例改成 0.1%，分母就要改成 0.001。

### 16. 为什么 FastBurn 要同时看 5m 和 1h？

只看 5m：

- 一次短暂尖峰就可能误报
- 低流量时比例波动大

只看 1h：

- 发现太慢

两个都看：

```text
5m > 14.4 且 1h > 14.4
```

既能在几分钟内发现持续错误，又不会被单次尖峰骗到。

SlowBurn 的 30m/6h 是同样的思路，只是时间尺度更长，代价是恢复也慢。

### 17. AlertmanagerConfig 和直接改 `alertmanager.yaml` 有什么区别？

直接改 `alertmanager.yaml`：

- 要自己管理 Secret/ConfigMap
- 要自己触发 reload
- 容易被 Helm 升级覆盖
- 多团队配置容易冲突

`AlertmanagerConfig`：

- 是 Kubernetes CRD
- Operator 监听并合并到最终配置
- 可以用 Git 管理
- 多个配置片段可以分开维护

但它不是立即生效，也不是直接可读；最终要检查：

```bash
kubectl exec -n monitoring alertmanager-kube-prometheus-stack-alertmanager-0 \
  -c alertmanager -- zcat /etc/alertmanager/config/alertmanager.yaml.gz
```

### 18. 抑制和静默分别在什么场景用？

| 项 | 抑制 | 静默 |
|---|---|---|
| 谁触发 | 规则自动 | 人手动 |
| 生命周期 | 源告警存在时一直有效 | 指定开始/结束时间 |
| 典型场景 | critical 压掉同服务 warning | 维护窗口、已知噪声 |
| 是否等于恢复 | 否 | 否 |

抑制解决“同一个问题不要重复报”，静默解决“这段时间先别报”。

静默删除后，如果条件仍然成立，通知会恢复。

### 19. 为什么 loadgen 只跑 0.5 req/s？

```text
INTERVAL_SECONDS=2
-> 约 0.5 req/s
```

5 分钟大约 150 个请求，足够计算成功比例；一天约 4.3 万请求，不会把 Loki/Tempo 写爆。

如果跑几十 req/s：

- 日志和 trace 量会明显增加
- 16 GB 实验环境更容易吃紧
- 对验证 SLO 逻辑没有额外帮助
