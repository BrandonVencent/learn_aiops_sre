### 2. 为什么 Loki 用 `Monolithic`，不是 `SingleBinary`？

#### 问题

Loki chart 的 values 里应该写 `deploymentMode: Monolithic` 还是 `SingleBinary`？

#### 结论

当前 `grafana-community/loki` chart `19.0.3` 使用 `Monolithic`。`SingleBinary` 是旧命名，继续照旧教程写会混淆。

单机学习环境用 `Monolithic` 就够了：

- 只有一个 Loki 实例。
- 使用文件系统存储。
- 不需要读写分离、分布式缓存和 MinIO。
- 资源占用小，适合 3 GB 内存的 worker。

安装时仍然通过 `singleBinary.replicas: 1` 控制实际副本。

### 3. 为什么把 Loki 放在 `k8s-worker-2`？

#### 问题

Loki 为什么固定到 `k8s-worker-2`，而不是随便调度？

#### 结论

因为 Loki 使用 `local-path` PVC，数据落在节点本地磁盘。如果 Pod 换节点，旧数据不会自动跟过去。

预检结果：

- worker-2 根分区：`/dev/sda3`，98G，已用 13G，可用 80G。
- worker-2 内存：total 2.9Gi，available 2.0Gi。
- Loki 计划 request `256Mi`，limit `1Gi`，空间和内存都够。
- server 上已经跑 Prometheus/Grafana，worker-2 只有系统组件，压力更小。

因此 values 里写了：

```yaml
singleBinary:
  nodeSelector:
    kubernetes.io/hostname: k8s-worker-2
```

### 4. `/var/lib/rancher/k3s/storage` 不存在，正常吗？

#### 问题

在 worker-2 上执行 `ls /var/lib/rancher/k3s` 只看到 `agent` 和 `data`，没有 `storage`，是不是 local-path 坏了？

#### 结论

正常。`local-path` provisioner 会在第一次有 PVC 需要绑定到该节点时创建存储目录。现在还没有 Loki PVC，所以目录不存在。

预检时用的是：

```bash
df -h /var/lib/rancher/k3s/storage
df -h /var/lib/rancher/k3s
```

第二条能看到目录所在分区，worker-2 根分区还有 80G，足够 5Gi PVC。不要手工 `mkdir` 一个空目录来“修复”，先让 local-path 自己创建。

### 6. `helm lint grafana-community/loki` 为什么报 `Chart.yaml` 不存在？

#### 问题

执行：

```bash
helm lint grafana-community/loki -f /root/logging/values-loki.yaml
```

报错：

```text
Error unable to check Chart.yaml file in chart: stat grafana-community/loki/Chart.yaml: no such file or directory
Error: 1 chart(s) linted, 1 chart(s) failed
```

#### 根因

不是 values 写错，也不是 chart 不存在。

`helm lint` 的第一个参数必须是**本地 chart 目录**。`grafana-community/loki` 是 Helm 仓库里的 chart 引用，不是文件系统路径；`helm lint` 不会像 `helm install` 那样去仓库解析它，而是直接把它当成目录，所以找不到 `Chart.yaml`。

#### 修复

先把 chart 拉到本地，再 lint：

```bash
mkdir -p /tmp/helm-charts
helm pull grafana-community/loki --version 19.0.3 --untar -d /tmp/helm-charts
helm pull fluent/fluent-bit --version 0.58.3 --untar -d /tmp/helm-charts

helm lint /tmp/helm-charts/loki -f /root/logging/values-loki.yaml
helm lint /tmp/helm-charts/fluent-bit -f /root/logging/values-fluent-bit.yaml
```

预期：

```text
1 chart(s) linted, 0 chart(s) failed
```

#### 备选

如果只想验证模板能不能渲染，可以直接 `helm template`：

```bash
helm template loki grafana-community/loki \
  --namespace logging \
  --version 19.0.3 \
  -f /root/logging/values-loki.yaml > /tmp/loki-rendered.yaml
```

但 `lint` 更严格，建议至少做一次本地 chart 的 lint。

### 9. 为什么 `helm template` 会多出 `loki-memcached`？

#### 问题

`values-loki.yaml` 里已经把 `chunksCache.enabled` 和 `resultsCache.enabled` 都设成 `false`，为什么渲染结果里还有 `loki-memcached` 的 ServiceAccount 和 Service？

#### 结论

因为 Loki chart 里有四个相关开关，不只两个：

| 开关 | 作用 |
|---|---|
| `chunksCache.enabled` | Loki 是否使用 chunk 查询缓存 |
| `resultsCache.enabled` | Loki 是否使用查询结果缓存 |
| `memcached.enabled` | 是否部署 chart 自带的 Memcached 服务 |
| `memcachedExporter.enabled` | 是否部署 Memcached 指标 exporter |

前两个是“Loki 客户端要不要用缓存”，后两个是“要不要真的部署 Memcached 服务”。只关前两个，`memcached.enabled` 默认仍是 `true`，所以 chart 仍会渲染 Memcached 相关的 ServiceAccount 和 Service。

这些对象不影响 Loki 本体启动，但属于无用资源，也会干扰“渲染结果是否符合预期”的判断。

修正：

```yaml
chunksCache:
  enabled: false
resultsCache:
  enabled: false
memcached:
  enabled: false
memcachedExporter:
  enabled: false
```

修正后重新渲染，Service 仍然有 3 个，但都不是 memcached：

- Service `loki`：ClusterIP，端口 `3100`，给 Fluent Bit 和 Grafana 用。
- Service `loki-headless`：StatefulSet 的 headless Service，给 Pod 稳定 DNS。
- Service `loki-memberlist`：headless，端口 `7946`，Loki 内部 memberlist ring 使用。
- StatefulSet `loki`：1 个副本。
- 不再出现 `loki-memcached`。

这里一开始把第三个 Service 误认为 memcached 残留，实际它是 `loki-memberlist`，属于 Loki 的正常结构。

#### 验证

```bash
grep -n '^kind:' /tmp/loki-rendered.yaml
grep -n -i 'memcached' /tmp/loki-rendered.yaml || echo "OK: 没有 memcached 对象"
```

预期：`memcached` 没有任何输出。

### 10. 为什么要关掉 Loki 的 `k8s-sidecar`？

#### 问题

渲染出的 Loki StatefulSet 里除了 `loki` 容器，还有一个 `kiwigrid/k8s-sidecar` 容器，它是做什么的？要不要保留？

#### 结论

这是 Loki chart 的 rules sidecar，用来监听带 `loki_rule` 标签的 ConfigMap/Secret，把 ruler 规则加载给 Loki。

当前阶段：

- 我们不做 Loki 告警规则。
- 这个 sidecar 默认没有 `requests/limits`，不符合“长期组件要有资源边界”的约定。
- 多一个容器就多一个排错点。

所以在 values 里显式关闭：

```yaml
singleBinary:
  sidecar: false

sidecar:
  rules:
    enabled: false
```

关闭后，Loki Pod 只保留 Loki 本体容器。以后要做 ruler 规则时，再打开并给 sidecar 配资源。

#### 验证

```bash
grep -n 'k8s-sidecar' /tmp/loki-rendered.yaml || echo "OK: 没有 rules sidecar"
```

预期：没有输出。

### 11. `/ready`、`/metrics`、`/buildinfo` 分别在验证什么？

#### 问题

Loki 安装后，为什么既要看 `/ready`，又要看 `/metrics` 和 `/buildinfo`？

#### 结论

三个端点回答不同问题：

| 端点 | 验证什么 | 预期 |
|---|---|---|
| `/ready` | Loki 是否准备好接收请求 | `ready` |
| `/metrics` | Loki 是否在暴露 Prometheus 指标 | 以 `# HELP`、`# TYPE` 开头的文本 |
| `/loki/api/v1/status/buildinfo` | 实际运行的 Loki 版本 | JSON 里的 `version` 是 `3.7.9` |

`/ready` 是“能不能用”，`/metrics` 是“可观测性有没有起来”，`/buildinfo` 是“版本对不对”。三个都通过，才能说 Loki 安装完成。

### 12. Fluent Bit 渲染出的 Service 和 Pod 是干什么的？

#### 问题

`helm template fluent-bit` 的结果里有：

```text
kind: Service
name: fluent-bit
port: 2020

kind: Pod
image: busybox:latest
```

我们不是只要 DaemonSet 吗？为什么还有 Service 和 Pod？

#### 结论

两者用途不同。

##### Service `fluent-bit:2020`

这是 Fluent Bit 自己的 HTTP metrics/health Service，不是日志入口。

Fluent Bit 的 `[SERVICE]` 配置里有：

```ini
HTTP_Server On
HTTP_Listen 0.0.0.0
HTTP_Port 2020
Health_Check On
```

所以 Service 暴露的是：

- Fluent Bit 指标 `/api/v2/metrics/prometheus`
- 健康检查端点

日志仍然是 Fluent Bit 主动推送到 Loki 的 `loki:3100`，不经过这个 Service。

##### `busybox:latest` Pod

这是 chart 默认的 Helm test Pod，由：

```yaml
testFramework:
  enabled: true
```

控制，用于 `helm test` 的连接测试。

它不参与正常日志采集。为了减少渲染结果里的干扰，本阶段关闭：

```yaml
testFramework:
  enabled: false
```

### 13. 为什么 `kubectl exec ... ls /var/log/containers` 报 `ls: executable file not found`？

#### 问题

想确认 Fluent Bit 是否看到了宿主机日志目录，执行：

```bash
kubectl exec -n logging "$POD" -- ls -l /var/log/containers
```

报错：

```text
OCI runtime exec failed: exec: "ls": executable file not found in $PATH
```

这是不是说明 `/var/log` 没挂载？

#### 结论

不是。

`fluent/fluent-bit:5.1.3` 是精简镜像，里面只有 Fluent Bit 自己的二进制，没有 `ls`、`sh`、`cat` 这些常用工具。`kubectl exec` 找不到 `ls`，说明镜像里没有这个命令，不说明挂载失败。

更可靠的判断方式：

1. 看 Pod 的 volumeMounts：

```bash
kubectl describe pod -n logging "$POD" | grep -A8 'Mounts:'
```

2. 看 Loki 是否已经收到带 `namespace/pod/container` 的日志：

```bash
curl -s http://127.0.0.1:3100/loki/api/v1/labels | python3 -m json.tool
```

如果 `labels` 里有 `namespace`、`pod`、`container`，说明 Fluent Bit 已经读到了日志，并且 Kubernetes filter 也工作了。

本次结果：

```json
{
  "status": "success",
  "data": ["container", "job", "namespace", "pod", "service_name"]
}
```

`service_name` 是 Loki/Fluent Bit 额外发现的标签，先保留；后面查日志时确认它的基数不要过高即可。

#### 经验

- 不是所有镜像都有 shell 和 coreutils。
- `kubectl exec ... ls` 失败不等于挂载失败。
- 优先用 `kubectl describe pod` 看声明，用 Loki 查询看实际效果。

### 14. 为什么 Loki 里的日志是 `{"_p":"F","log":"..."}`？

#### 问题

查询 Loki 得到的日志行不是应用原始内容，而是：

```json
{"_p":"F","log":"level=info ..."}
```

这两个字段是什么？

#### 结论

`_p` 是 CRI 日志解析器加上的“完整/部分行”标记：

- `F`：full，完整行。
- `P`：partial，多行日志的未完成部分。

`cri` 解析器会用这个字段把容器运行时因为长度限制而拆开的同一行拼回来；它不负责合并应用自己的 Python traceback。当前 output 没有删除 `_p`，所以 `Line_Format json` 把它一起输出了。

`log` 是应用原始日志内容。因为我们设置了 `Merge_Log Off`，Fluent Bit 不会把 `log` 里的 JSON 字段展开，所以应用日志仍然是 `log` 里的一个字符串。

这对“日志能进 Loki”没有影响，但会影响下一步的 `level` 过滤：

```logql
{namespace="demo"} | json | level="error"
```

第一次 `| json` 解析的是外层 `{"_p":"F","log":"..."}`，只能得到 `_p` 和 `log`，不能直接得到 `level`。

已经验证：嵌套写法可以取到 `level`：

```logql
{namespace="demo", pod=~"log-demo-.*"}
  | json
  | line_format "{{.log}}"
  | json
  | level="error"
```

原理见 Q&A #18。后续如果要支持简单写法，再把 `Merge_Log Off` 改成 `Merge_Log On`，并把 `_p` 加进 `Remove_Keys`；不要和 multiline 修复同时改。

### 15. `kubectl exec ... python - <<'PY'` 为什么没有任何输出？

#### 问题

执行：

```bash
kubectl exec -n demo deploy/log-demo -- python - <<'PY'
import urllib.request
...
PY
```

命令直接返回，没有任何输出，日志里也没有 `/error`。

#### 结论

少了 `-i`。

`kubectl exec` 默认不把本地标准输入接到容器里。heredoc 的内容没有被送进 `python -`，Python 读到空输入后立即退出，所以请求根本没有发出去。

正确写法：

```bash
kubectl exec -i -n demo deploy/log-demo -- python - <<'PY'
import urllib.request

try:
    urllib.request.urlopen("http://127.0.0.1:8080/error")
except Exception as exc:
    print("request result:", type(exc).__name__, exc)
PY
```

- `-i`：把 stdin 接进容器。
- `-t`：分配 TTY，heredoc 场景通常不需要，加了反而可能多出控制字符。

#### 经验

- `kubectl exec` 不写 `-i` 时，heredoc 不会生效。
- 命令“成功返回但完全没输出”本身就是一个线索，不要只看退出码。
- 先用 `/` 验证应用能响应，再用 `/error` 触发错误日志。

### 16. Grafana 的 Loki 健康检查为什么打到 `localhost:3100`？

#### 问题

Grafana 里点 `Save & test`，日志显示：

```text
Loki health check failed
Get "http://localhost:3100/loki/api/v1/query": dial tcp [::1]:3100: connection refused
```

但 Loki Service 明明是 `loki.logging.svc.cluster.local:3100`。

#### 结论

当时 Grafana 里测试的不是 provisioning 的 `Loki`，而是一个旧的手工数据源 `loki`，它的 URL 被填成了 `http://localhost:3100`。

判断依据：

- 旧数据源：`dsName=loki`，`dsUid=dg1zqi7tex9fke`，UID 是 Grafana 自动生成的。
- provisioning 数据源：`dsName=Loki`，`dsUid=loki`，URL 是 `http://loki.logging.svc.cluster.local:3100`。

`localhost` 在 Grafana Pod 里指向 Grafana 自己，不是 Loki，所以连接被拒绝。

#### 处理

在 `Connections → Data sources` 里把旧数据源的 URL 改成：

```text
http://loki.logging.svc.cluster.local:3100
```

修改后健康检查返回：

```text
status=ok
lokiHost=loki.logging.svc.cluster.local:3100
```

建议保留 provisioning 的 `Loki`，删除旧的手工 `loki`，避免以后选错。

#### 经验

- Grafana 数据源列表里名字相似时，要看 UID 和 URL，不要只看名字。
- `localhost` 是 Pod 内部地址，不是节点地址，也不是 Service 地址。
- provisioning 数据源通常是只读的，手工数据源可编辑；能直接改 URL 的往往是旧的手工数据源。

### 17. Grafana sidecar 报 `401 Invalid username or password`，数据源还能用吗？

#### 问题

`grafana-sc-datasources` 日志：

```text
Writing /etc/grafana/provisioning/datasources/loki-datasource.yaml (ascii)
None sent to http://localhost:3000/api/admin/provisioning/datasources/reload

```

#### 结论

能用的部分：

- sidecar 已经成功把 provisioning 文件写进共享目录。

1. 接受 401，数据源变更后手动重启 Grafana。
   简单，适合当前学习环境。
2. 把 Grafana 当前 admin 密码同步到 sidecar 使用的 Secret。

### 18. 为什么 `| json | level="error"` 为空，而嵌套写法能查到？

#### 问题

Loki 里已经能看到 error 日志，但：

```logql
{namespace="demo", pod=~"log-demo-.*"} | json | level="error"
```

返回空。改用：

```logql
{namespace="demo", pod=~"log-demo-.*"}
  | json
  | line_format "{{.log}}"
  | json
  | level="error"
```

就能返回 error JSON。为什么？

#### 结论

因为 Loki 里保存的每一行不是应用原始 JSON，而是 Fluent Bit 外层又包了一层：

```json
{"_p":"F","log":"{\"ts\":\"...\",\"level\":\"error\",...}"}
```

第一条查询只做一次 `| json`，解析结果只有外层字段：

```text
_p = F
log = {"ts":"...","level":"error",...}
```

`level` 在 `log` 这个字符串里面，不在外层，所以 `level="error"` 匹配不到。

嵌套写法做了两次解析：

1. 第一次 `| json`：解析外层，得到 `log`。
2. `| line_format "{{.log}}"`：把 `log` 的内容变成新的日志行。
3. 第二次 `| json`：解析应用自己的 JSON，得到 `level`。
4. `| level="error"`：过滤 error。

#### 验证

返回结果中能看到：

```json
{
  "ts": "2026-10-22T13:07:57.488991+00:00",
  "level": "error",
  "service": "log-demo",
  "trace_id": "demo-trace-001",
  "message": "demo error for Loki"
}
```

#### 处理

当前阶段先用嵌套写法完成验收，不改 Fluent Bit 的 `Merge_Log`。

后续如果要支持简单的 `| json | level="error"`，可以单独做一次配置变更：

- `Merge_Log On`：把应用 JSON 展开到记录顶层。
- 把 `_p` 加入 `Remove_Keys`，去掉 CRI 内部标记。

不要和 traceback 的 multiline 修复同时改，否则无法判断是哪个配置让查询生效。

<a id="qa-19"></a>
### 19. Python traceback 为什么一开始被拆成多条？

#### 问题

应用容器日志里明明是连续的：

```text
Traceback (most recent call last):
  File "/app/app.py", line 39, in do_GET
    raise RuntimeError("demo error for Loki")
RuntimeError: demo error for Loki
```

但 Loki 里只有：

```json
{"_p":"F","log":"Traceback (most recent call last):"}
```

后续 `File ...`、`raise ...`、`RuntimeError ...` 都变成了独立记录。

#### 根因

原来的 Tail 配置是：

```ini
multiline.parser cri, python
```

`cri` 负责 CRI 运行时拆行；但应用自己的 Python 堆栈没有在这个组合下合并成功。

Fluent Bit 的推荐分层是：

- Tail + `cri`：处理容器运行时把一行拆成多段的情况。
- 单独的 `multiline` filter + `python`：在 CRI 解析之后，合并应用自己的 Python 堆栈。

也就是说，CRI 解析和应用堆栈合并是两层，不应该只依赖 Tail 的 `cri, python`。

#### 修复

```ini
# Tail 只保留 CRI
multiline.parser cri
```

```ini
# 必须是第一个 filter
[FILTER]
    Name multiline
    Match kube.*
    multiline.key_content log
    multiline.parser python

[FILTER]
    Name kubernetes
    Match kube.*
    Merge_Log Off
```

为什么不加 `Buffer On`：

- 官方文档说明 Tail 输入是例外，multiline filter 可以按 chunk 处理。
- 先保持最小配置；只有确认 traceback 跨 chunk 到达、仍然拆开时，才加 `Buffer On`。

为什么必须在 `kubernetes` 前面：

- multiline filter 会把合并后的记录重新送回 pipeline 头部。
- 它自己是第一个 filter，会忽略自己重新送回的记录。
- 如果前面还有 filter，那些 filter 会被执行第二次。

#### 验证

重新触发 `/error` 后查询：

```logql
{namespace="demo"} |= "Traceback"
```

结果是 1 个 values 条目，`line` 为：

```json
{
  "_p": "F",
  "log": "Traceback (most recent call last):\n  File \"/app/app.py\", line 39, in do_GET\n    raise RuntimeError(\"demo error for Loki\")\nRuntimeError: demo error for Loki"
}
```

说明 `Traceback`、`File`、`raise`、`RuntimeError` 已经在同一条记录里。

`_p` 还在是正常的：这次只修多行合并，没有改 `Remove_Keys`。如果要清理外层包装，需要另外做 `Merge_Log`/`Remove_Keys` 变更。

#### 经验

- “日志能进 Loki”和“多行日志合并成一条”是两个验收点。
- 看到 `_p` 不代表多行解析成功；要看 traceback 后续行是否在同一条 `line` 里。
- 不要一次同时改 Tail parser、multiline filter、Merge_Log 和 output，否则无法判断哪个变量生效。
