## Q&A

### 1. 部署时遇到过什么问题？怎么发现的？怎么解决？

按"现象 → 发现 → 定位 → 修复"讲四个。

#### Grafana OOMKilled

- 现象：Pod 反复重启。
- 发现：`kubectl describe pod`，`Last State: OOMKilled`。
- 定位：Grafana 13.2.4 启动加载 56 个插件，limit 只有 256Mi。
- 修复：提到 512Mi，RESTARTS 归零，事件不再出现 OOM。如果 512Mi 还 OOM，下一步 768Mi，一次只改一个参数。
- 经验：换版本（Grafana 13）内存预估要重做。

#### Tempo 首次安装失败

- 现象：`helm upgrade --install` 报 connection reset。
- 发现：报错发生在下载 `tempo-3.2.1.tgz` 阶段，Kubernetes 资源还没创建，排除集群问题。
- 修复：Windows 下载同一官方 chart，SHA256 校验，解压核对 `Chart.yaml` 的 `version` / `appVersion`，`scp` 到 server 本地安装成功。
- 经验：网络受限环境要有"离线产物 + 校验"的习惯，不能只重试。

#### OTel Collector exporter 别名

- 发现：collector 日志 `otlp alias is deprecated`。
- 定位：0.163.2 中 gRPC exporter 的名字是 `otlp_grpc`，`otlp` 是兼容别名；receiver 仍叫 `otlp`。
- 修复：改 exporter 名，滚动重启，warning 消失。
- 经验：锁版本要读 changelog；改名类变更要隔离到受影响的字段。

#### ai-summary startupProbe 被杀

- 发现：`RESTARTS=2`，日志每次停在 `pip install`。
- 定位：startupProbe 总预算 150s 小于清华源最慢安装时间。
- 修复：`failureThreshold` 30→60（300s），新 Pod 0 重启；根治要预构建镜像。
- 经验：探针预算按"最慢可能值"定，而不是"通常值"。

### 2. 后续还会遇到吗？可以预防吗？

| 类型 | 预防 | 性质 |
|---|---|---|
| 环境依赖类（网络、安装） | 预构建镜像、chart 离线缓存 + SHA256、快照回滚 | 可根治 |
| 集成细节类（钉钉渲染、LLM 漂移、probe 预算） | 每次修复写成可复跑的验证命令，加进验收清单；改 ConfigMap 必须 rollout restart | 可能再出现，出现时快速确认 |

配套动作：ai-summary 有 `/metrics` 自监控；修复同步登记到 QA；代码配置和 VM 快照双向回滚。

### 3. 有备用方案吗？需要准备备用方案吗？

按爆炸半径排序，逐个回答"什么时候切、谁来切、怎么验证切换成功"：

| 单点 | 主方案 | 备用 | 状态 |
|---|---|---|---|
| 通知 | 钉钉加签 | `continue` 双路到 alert-webhook；邮件 webhook 已预留未启用 | 双路已做，邮件未启用 |
| LLM | DeepSeek | 规则降级模板；OpenAI 兼容接口可换 provider | 已实现 |
| 安装/网络 | GitHub / Docker Hub | chart 离线缓存 + SHA256 + 镜像加速 | 已做 |
| 数据源 | Loki / Tempo 单副本 | 无 | 实验取舍，记为已知偏差 |

原则：备用方案不只是"技术上有"，必须定义切换条件和执行者。实验里切换员是人，生产要自动化 + runbook。

### 4. 对接手生产工作有什么帮助？

四个帮助：

1. 会读别人的 values/manifests 并能说出字段影响面；
2. 排障按 SLO → 三类证据交叉核对的固定顺序，结论可复现；
3. 变更有纪律：先基线再动手，验收清单 + 快照；
4. 清楚 AI 的权力边界：模型只归纳，校验和降级在服务端。

诚实边界：没有真实 on-call、容量规划、多团队协作经验；故障合成、流量自造。项目把"能直接接手什么"和"需要带入什么"划清了。

### 5. 为什么要做这个项目？

两个动因：

1. 补"为什么每一跳存在"这一课——验收标准是能画出数据从产生到被 AI 使用的完整路径并解释每一跳；
2. 验证 AI 在运维场景的约束怎么落地：结论挂证据、数字用手工查询复现、模型失效有兜底。

坦白：这是个人实验，故障合成、流量自造，但问题来自真实场景（值班告警只说结果不说原因），方法用生产方法：基线、验收、快照、审计式记录。

### 6. 端到端数据流转（面试深入题：日志报错 / Pod 不 Ready → 告警 → AI → 钉钉）

关键澄清：两类故障的信号路径不同。

| 故障类型 | 信号产生处 | 触发告警 |
|---|---|---|
| 应用内报错 500 | demo 自写 counter | FastBurn |
| Pod 重启 / NotReady | demo 无数据，counter 不增长；loadgen 失败不计入 | NoTraffic 兜底 |

结论：告警对「变慢」「变错」敏感，对「瞬间消失」靠 NoTraffic。

六步流转（全部对上代码）：

1. **t=0**：demo 同一时刻做三件事——counter 自增（path 白名单）、stdout JSON 日志（trace_id/span_id）、OTel span（错误标 ERROR）；`/healthz`、`/metrics` 不产生业务数据。
2. **采集**：ServiceMonitor 15s 抓 `/metrics`；Fluent Bit → Loki 补标签；OTel → Collector → Tempo。recording rule 每 30s 预算四窗口 SLI/燃烧率。
3. **规则**：FastBurn 双窗 >14.4 `for: 2m` → 15:11:09 active（6b 实测，注入后约 11 分钟，是双窗 + for 的代价）。
4. **Alertmanager**：`groupWait: 10s` 攒组，15:11:19 发出；`continue: true` 双路（原 webhook + ai-summary）；inhibit 压 warning。
5. **ai-summary**（15:11:19 → 15:11:23）：
   - webhook 层：`dedup_key = groupKey + alertnames`（resolved 加后缀），600s 指纹，重复 202 跳过；11.8ms 返回 202；
   - resolved 状态走 `handle_resolved`，不调模型；
   - `collect_evidence`：10 条固定 PromQL + Loki 双层 JSON + Tempo 前 2 条错误 trace（T1 错误 span 数、T2 最大 inventory.call 时长），非有限值过滤；
   - `is_timeout_scenario` / `compute_priority` / `compute_confidence` 全在服务端；
   - 三段提示词：`<alert>`（脱敏 annotations，标为人类假设）、`<evidence>`（id+sky query+value）、`<untrusted_logs>`（编号，声明忽略指令）；
   - DeepSeek 返回剥围栏 → pydantic → 证据 ID 拆分归一匹配，无一条有效引用直接 ValueError → fallback；4xx/5xx 或非法 JSON 有一轮自动 repair；`matched<2` 强制「证据不足」+ 低置信度标题；
   - 卡片渲染纯文本、M5 格式 `/checkout（504）`；钉钉加签 HMAC-SHA256（时间戳毫秒 + 换行 + secret）；15:11:24 到群，端到端约 5 秒。
6. **resolved**：`sendResolved` payload `status="resolved"` → `handle_resolved` 算持续时长直接发恢复卡（15:22:50）；SlowBurn P2（15:22:52）为长窗残留已知偏差。

三个追问的口径：

| 追问 | 要点 |
|---|---|
| 202 之后为什么还要去重？失败怎么办？ | 重复投递是 Alertmanager 正常行为，fast-path 省一次模型调用；202 失败由 Alertmanager 退避重试，下一轮再过指纹，天然幂等。 |
| AI 为什么不自己写 PromQL？ | 可能语法对但口径错；固定查询保证与 Grafana 同口径、可复核；把模型隔离在查询路径外，降低被日志指令带偏的风险。 |
| P95 很慢为什么 P1？ | 优先级由 firing 告警定：FastBurn critical 且 burn5m>14.4 → P1；P95 只影响置信度命中数，不参与定级。 |
